# Полный аудит кодовой базы RealTimeAlertingService

## Что оставить

- Базовое разделение на домен/инфраструктуру/сервисы — верное направление.
- Есть попытка использовать `Clock` для тестируемости времени.
- Есть in-memory реализации репозиториев для простого unit-тестирования.
- В домене есть явные состояния алерта и бизнес-методы жизненного цикла.

## Что критично исправить (P0)

1. **Сломанная JPA-модель (доменные классы аннотируются как связи JPA)**
   - `AlertEntity` ссылается на доменные `AlertRule` и `Event`, а не на `AlertRuleEntity`/`EventEntity`.
   - `AlertRuleEntity` хранит `Condition` как `@ManyToOne`, хотя `Condition` не является JPA Entity.
   - Это не «архитектурный компромисс», а прямая неработоспособность persistence-слоя.

2. **`id` не генерируются в `AlertEntity` и `AlertRuleEntity`**
   - Для первичных ключей нет `@GeneratedValue`, но в коде создания сущностей id не заполняется.
   - При сохранении будет `null`-id/ошибки на уровне БД.

3. **Spring wiring фактически не соберётся корректно**
   - Адаптеры репозиториев и мапперы не помечены как Spring beans (`@Repository`/`@Component`).
   - `AlertProcessingService` и `AlertRuleService` требуют `Clock`, но bean `Clock` не объявлен.

4. **POM в неконсистентном состоянии для воспроизводимой сборки**
   - Maven-сборка в текущем окружении не проходит (невозможно резолвить parent).
   - В `pom.xml` присутствуют вручную зафиксированные версии библиотек, которые Spring Boot обычно управляет через BOM.

## Что исправить срочно (P1)

1. **`AlertRuleService` содержит `static Clock` + `static createAlertRule`**
   - Это ломает изоляцию тестов и вносит глобальное состояние.

2. **`AlertService` мутирует правило во время обработки события**
   - Для `CRITICAL` меняется `maxRetries` прямо в runtime у правила.
   - Логика сервиса смешивает бизнес-правила, побочные эффекты и `System.out.println`.

3. **Грязный API и naming**
   - Методы `getAllAlert`, `saveAlertRule`, `findRuleByEvent` и т.д. не выдерживают единый стиль.
   - `getSourceType/getSourceName` в `AlertRule` на самом деле возвращают `eventType/eventField`.

4. **Event mapping проглатывает ошибки**
   - В `EventMapper.deserializePayload` неизвестные поля silently игнорируются.
   - Исключения сериализации/десериализации бросаются как `RuntimeException`, хотя есть `EventMappingException`.

5. **Тесты в текущем виде недостаточно надёжны**
   - Много тестов завязаны на `id=1L` и косвенное состояние репозитория.
   - Есть лишние/неиспользуемые импорты и неиспользуемые поля времени (`otherClock`).

## Что улучшить (P2)

1. Добавить полноценный REST API для управления правилами/алертами/событиями (сейчас `/events` возвращает `hello world`).
2. Ввести DTO + валидацию входа (`jakarta.validation`) + `@ControllerAdvice` для ошибок.
3. Сформировать миграции (`Flyway`/`Liquibase`) и явную схему таблиц.
4. Добавить метрики/логирование (`slf4j`) вместо `System.out.println`.
5. Вынести retry/cooldown/resolve-логику в unit-tested use-case слои.

## Что убрать

- Закомментированный «песочничный» код из `main`.
- Лишние/неиспользуемые импорты.
- Неиспользуемый класс `RawData` (или интегрировать его в ingestion pipeline).
- Мёртвые и дублирующие методы/конструкторы, если они не нужны.

## Рекомендуемый минимальный план рефакторинга

1. Починить JPA-модель: только entity-ко-entity связи, ключи, генерацию id.
2. Добавить Spring-конфигурацию bean’ов (`Clock`, mapper’ы, repository adapters).
3. Убрать static-состояние из сервисов.
4. Переписать `AlertService` в отдельный use-case без мутации правил и без stdout.
5. Укрепить тесты: deterministic id, явные сценарии переходов состояний, негативные кейсы маппинга.
